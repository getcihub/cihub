# Queue algorithms

A single algorithm covers the simple mode, the parallel mode, batching and bisection: one **reconciler** per queue recomputes a dependency graph (the merge graph) from the ordered list of admitted items, and a test run is valid only as long as the set of predecessors of the group and the base SHA are unchanged. Each function below is either a rule for building this graph or a rule for reacting to its change.

**Conditions.** A queue declares two distinct sets of conditions, because confusing them is the most cited limit of the native GitHub queue: `queue_conditions` says what a PR must satisfy to be admitted (reviews, labels, author, touched files, checks on the PR itself) and `merge_conditions` what the speculative commit must satisfy to be merged (the required checks on the test branch, at least). The checks required by the rules of the target branch are injected according to `branch_protection_injection` (`DECISIONS.md` D147): `both` (default) adds them to the `queue_conditions`, as `check-success = <name>` on the head of the PR (without the queue status, D105), and to the required statuses of the test SHA; `merge` adds them only to the test SHA; `none` adds them nowhere. For now, `merge_conditions` accepts only top-level `check-success = <name>` conditions, whose names are added to the required statuses of the run (D146). The language is deliberately small: a condition is `[-] attribute [op value]` with `=`, `!=`, `~=` (regex), `*=` (glob), `<`, `<=`, `>`, `>=`, `#attribute` for a length, and `and`, `or`, `not` blocks; about thirty attributes (list in `cihub-conditions`) cover the state of the PR, the reviews, the checks, the labels, the author, the files, the base and the head, the position and the age in the queue, and the time. The same language serves for routing between queues of the same branch and for `priority_rules`. The jobs that read a PR evaluate its `queue_conditions` and return the ones that are not satisfied in `pr.observed`; the item then stays in `not_ready` with the block reason `queue_conditions_unmet`. Conditions count only before admission: a condition that becomes false does not remove an admitted item (`DECISIONS.md` D142). `sender` and `sender-permission` come from the submission (D144).

The syntax and the attribute names are specific to CIHub; no alias is accepted (`DECISIONS.md` D139). Vocabulary (the code of `cihub-conditions` is authoritative):

Syntax rules:

- One symbol per operator: no `:`, no `≠`, `≥`, `≤`.
- A boolean is written only `attribute` or `-attribute`; `draft = true` is an error. A string accepts `=`, `!=`, `~=` and `*=`; an integer, a duration and `sender-permission` accept `=`, `!=`, `<`, `<=`, `>`, `>=`; `review-decision` accepts `=` and `!=`.
- On a list, `=`, `~=` and `*=` are true if one element matches, and `!=` is true if no element is equal; `#list` compares the number of elements with the operators of an integer. An absent string (`sender`, `queue-name` outside the queue) behaves like an empty list; a comparison on an absent value (`queue-age` outside the queue, `sender-permission` without a sender) is false.
- `-attribute op value` is the negation of `attribute op value`: `-label = do-not-merge` is true when no label equals `do-not-merge`.
- The value runs to the end of the condition, without the spaces at both ends (`author = dependabot[bot]`), or between double quotes with `\"` and `\\` as escapes.
- `~=` looks for a match anywhere in the string with the `regex` crate, in guaranteed linear time, which protects a shared instance; lookahead, lookbehind and backreferences are not accepted. `*=` compares the whole path with a glob where `*` does not cross `/` and `**` does.
- In `queue_conditions`, the checks are read on the head of the PR; in `merge_conditions`, on the test SHA. Names match exactly, without an `@app/` prefix. No templates (`{{ author }}`).
- A list of conditions is an `and`. A block is a single key `and`, `or` or `not` followed by a list; `not` is true when the whole list is not satisfied.
- An unknown attribute, an operator that does not fit the type or an invalid value gives an error with its column in the condition, which `cihub-config` completes with the line of the file.

**Strategies.** The individual settings (batching, optimistic merge, parallel mode, direct merge) remain available, but a queue is configured first by a named strategy, `strategy`, which sets them consistently; choosing a strategy and then adjusting a setting is allowed, and the interface then flags the deviation from the strategy.

| `strategy`           | What it enables                                                                                               | For whom                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `sequential`         | One PR tested at a time, `fast_forward` possible (`DECISIONS.md` D120); `inplace` with a later lot (D119)     | Small repositories, short CI, no temporary branch, no protection bypass                |
| `pipelined` (default) | Predictive tests with an adaptive window of 2–20, failure budget of 1 restart, no batches                    | Repositories with moderate traffic                                                     |
| `batched`            | Batches of dynamic size 2–8 with a 5 min wait, bisection, `pending_failure_depth` = 1, optimistic merge       | Long and costly CI, many PRs per hour                                                  |
| `parallel`           | Independent queues per impacted targets, batches per lane, optimistic merge                                   | Monorepos that publish their targets (Bazel, Nx, in-house script)                      |

Each strategy is a simple table of default values on the existing settings; adding a new one requires no code in the core.

**Order.** Each admitted item receives a `position` (spaced 64-bit integer) that fully determines its place; items are sorted by `position` alone, and `priority_value` decides only the insertion point of a new item. `urgent` (value 0) goes to the head, ahead of the groups already in test, which is the only insertion that invalidates a test in progress. Any other value is inserted before the first item that is not in test and whose `priority_value` is greater: `high` (10) items thus line up behind the groups in test, in FIFO order among themselves, and ahead of all `medium` (100) and `low` (200) items. Values 1 to 255 are accepted and never preempt.

**Merge graph.** Each item carries a set of targets `T(i)`: the impacted targets sent in parallel mode, or the `ALL` sentinel in simple mode (as well as for any PR that sent `ALL` or exceeded the 20 MB upload limit). Item `j` is a predecessor of `i` if `j` is ahead of `i` and there is a chain of items placed ahead of `i`, with pairwise overlapping target sets, that links `j` to `i`. Simple mode thus degenerates into a linear chain, and parallel mode produces independent lanes without ever naming them. An item is tested on top of exactly its predecessors and merges only once all its predecessors have merged.

**Predictive test branch.** For a group `G` with ordered predecessors `P1..Pk`, the executor creates `cihub-temp/pr-<N>/<run_uuid>` at the head SHA of the target (`base_sha`), merges `P1..Pk` into it and then the members of `G` with the GitHub merges API (one call per PR head SHA, in order; a 204 means already contained and counts as a success), then creates the `cihub-merge/pr-<N>/<run_uuid>` reference at the resulting SHA through the git refs API and deletes the temporary reference: the CI thus sees a single branch creation push, for the final commit, and none for the intermediate merges. The prefixes are configurable per queue and cannot change while the queue contains live items. A 409 on the merge of a group member ends the run with `start_test_run_merge_conflict` and a `conflict_culprit` (`docs/DOMAIN.md`): `base_branch` when the member does not merge onto `base_sha` alone, otherwise the first PR ahead of it that does not merge onto `base_sha` plus the member, found by a second pass of merges in the conflict case only. A 409 on the merge of a predecessor concludes nothing: the run of that predecessor meets the same conflict and decides, the job retries later and finds its run superseded. Three trigger modes: in `draft_pr` mode, the executor then opens a draft PR from the test branch to the target branch, so that the CI triggered on `pull_request` runs without modification, and the queue closes it at the end; in `push` mode, the CI must trigger on `cihub-merge/**`; in `inplace` mode, reserved for the `sequential` strategy, no branch is created: the PR branch is updated onto the target by a merge (`update_method: merge`, `DECISIONS.md` D114) and the CI of the PR itself is authoritative, which avoids any branch protection bypass requirement for small repositories; this mode arrives with a later lot (`DECISIONS.md` D119). At the end of a run, the `cleanup_test_branch` job closes the draft PR and deletes the branches after `keep_test_branches_minutes` (D117).

**End of run.** The names of the required statuses come, in order of precedence, from `.cihub.yaml` or `.cihub.yml` read on the target branch at `base_sha` (never from the PR, so that a PR cannot weaken its own barrier), then from the protection of the target branch: the union of the `required_status_checks` of the classic protection and of the repository and organization rulesets that match the branch. An empty result fails the run with `start_test_run_no_required_statuses`. The run stores every `check_run` and `status` reported for the test SHA and marks the required ones. It passes when each required name has a terminal conclusion `success`, `neutral` or `skipped`; it fails at the first `failure`, `error`, `cancelled`, `timed_out`, `action_required` or `stale`; it expires after `testing_timeout_minutes` (300 by default) with `test_run_timeout`. Names match exactly; a name that never reports gives a timeout, not a failure. Reports tied to a SHA of a cancelled or superseded run are stored then ignored (`DECISIONS.md` D118), and when the App has the optional `actions: write` permission, the executor cancels the running workflows of that run (after Lot 6, D116).

**Speculation window.** The number of groups tested at the same time is not a constant but an adaptive window, on the model of Zuul: `window.floor` (2 by default), `window.ceiling` (20), a current window that starts at the floor, grows by 1 at each successful run outside bisection and halves at each confirmed test failure (after the failure budget, or at bisection), without changing for a conflict, a configuration error or a merge failure (`DECISIONS.md` D141). A reduced window interrupts no run in progress. A healthy queue opens up to the ceiling; a queue hit by flaky tests closes by itself and stops wasting CI on runs bound to restart. `testing_concurrency: N` is a shortcut for `window: { floor: N, ceiling: N }`; the two settings are mutually exclusive. A batch occupies one slot in the window; bisection runs draw from a separate pool, `bisection_concurrency` (equal to the ceiling by default). Slots are assigned in graph order. When the SCM budget of the connection enters `throttled` mode, the window does not change: the assembly jobs, of class `speculate`, wait for the budget.

**Batching.** Disabled by default. The reconciler forms a batch from the longest series of consecutive waiting items that share a lane, are not `no_batch` and are not blocked, up to `batching.size` (4 by default). It starts the batch when it is full or when its oldest member has waited `batching.max_wait_minutes` (5 by default). A `no_batch` item keeps its position and forms a group of a single PR. Batches are tested predictively like single items; each member still merges as its own commit, in order.

**Bisection.** When the failure of a batch is confirmed (see pending failure), it is cut in two while preserving the order; the two halves become groups of kind `bisection` with the failed batch as parent, the first half inheriting the predecessors of the batch and the second depending in addition on the first. The predecessors of a group (`predecessor_ids`) are items and not groups, because the merge graph is defined on items: the second half thus has as predecessors those of the batch plus the items of the first half. Results are cached within a bisection: if the whole batch failed and the first half passes, the second is marked failed without a run (`test_run_failed_by_optimization`). Only the tested half goes back to `pending` (`bisection_required`); the items of the other half stay in `pending_failure` until the first concludes, then go to `failed` if it passes, or to `pending` to be tested if it fails. A failing half keeps splitting until it isolates single PRs; the halves that pass merge normally. Six PRs cost 2 to 4 runs instead of 6.

**Pending failure and depth.** A group whose run fails goes to `pending_failure` and waits for each predecessor to reach a final state. If a predecessor failed, was cancelled or changed shape, the group restarts (`prerequisite_merge_item_failed`, etc.) with its new set of predecessors. If all predecessors merged, the group is the culprit, unless `pending_failure_depth` is `N > 0`: it then also waits for the first `N` successor groups whose runs include it to finish **their runs** (and not to reach their final state, which avoids a mutual wait). The set of successors is reevaluated at each reconciliation: a group admitted behind the failed group after the failure, with overlapping targets, thus counts. A successor run that passes releases the group (`successor_test_run_passed`) if optimistic merge is active. Otherwise the group becomes `failed` (single PR) or is bisected (batch), and its successors restart without it.

**Failure budget.** A single failure is never enough to designate a culprit. When a group is in culprit position (all its predecessors merged, no successor released it), the queue first consumes its budget: `failure_budget.retries` (1 by default) restarts of the run, and only the failed jobs when the CI allows it (`actions: write`), before declaring it `failed`. The budget is increased by one restart when the `FlakeOracle` contract recognizes the failed tests, and set to zero when the failure is a merge conflict or a configuration error, which are never transient. Shopify reports that a threshold of three consecutive failures brings false evictions down to 0.4% with a quarter of flaky tests; CIHub exposes the threshold and publishes, per queue, the rate of evictions that proved unjustified (the PR resubmitted without change passed), so that the team tunes it on its own numbers.

**Optimistic merge.** Disabled by default. When it is active, a run that passes proves all the groups it was built on: the reconciler thus marks all the groups ahead of it still in `testing` as `tests_passed` (`passed_by_optimization`) and interrupts their runs, and marks those in `pending_failure` as `tests_passed` (`successor_test_run_passed`); each affected item records the run of the successor in `verified_by_run_id`. The first effect requires a window ceiling (`window.ceiling`) greater than 1; the second requires `pending_failure_depth > 0`, since at depth 0 a failed group is evicted as soon as its predecessors merge. CIHub always restarts the downstream groups when a predecessor is evicted, because their tests included code that will not land; this is the strict rule, and the lenient rule is in the open questions (`DECISIONS.md` Q3).

**Direct merge on main.** Disabled by default (`direct_merge_mode: off`, `DECISIONS.md` D153). With `always`, the first item of a `running` queue without a live group, in `pending`, receives a single direct merge attempt, without a test branch, and no group forms for it until the attempt has answered. The merge job checks before acting that the required statuses of a test commit on the current head of the target are green on the head of the PR, that the PR contains that head and that it is mergeable; it then merges the PR (`merge_graph_direct_merge`), otherwise the item follows the test path, without failure. With `squash`, `merge_commit` and `rebase`, a push on the target between the check and the merge is not detected; `fast_forward` refuses to advance a target that has moved.

**External changes.** A `push` on the target branch belongs to the queue when its `sender` is the bot account of the App (`cihub-io[bot]`) or when its `after` SHA equals a `merged_sha` recorded by a merge job; a push that arrives late (its `after` is a SHA older than the known head, or its `before` is a former head) changes nothing, and the tick rereads the real head; any other push invalidates all runs (the base SHA changed) and the affected groups restart with `manual_push_to_target_branch`. A PR of the queue merged outside the queue is marked `merged` (`manual_merge`) and its dependents restart with `prerequisite_merge_item_manually_merged`. A push on the head of a PR in the queue, a change of base branch, a switch to draft, a close or the removal of the entry label cancels the item with the matching reason; the PR must be resubmitted. Submissions by label are honored only for open, non-draft PRs.

**Merge step.** Groups merge strictly in graph order, and within a batch the members merge in batch order. Four methods: `squash`, `merge_commit` and `rebase` merge the original PR through the GitHub API with the `sha` guard set to the head SHA recorded at admission (a 409 gives `pr_updated_at_merge_time`); `fast_forward`, allowed only with the `sequential` strategy (`DECISIONS.md` D120), advances the target branch without force directly onto the tested commit, so that the commit that lands is exactly the one the CI saw, at the cost of a branch protection that allows the App to push and of a history made of merge commits; GitHub then marks the PR as merged by itself. If a member of a batch fails to merge, the members behind it in the same batch and all downstream groups restart, because their tests included the unmerged code. 5xx responses are retried 10 times over 60 s; a 405 "merge already in progress" is followed by a read of the PR and of the target branch, because the merge may have succeeded. The SHA of the merge commit is recorded as `merged_sha`, and the bot login is checked on incoming pushes, so that the merges of the queue are never taken for external changes. A `merge-commit-title: <title>` line in the body of the PR replaces the commit title for squash and merge commit.

**Timeouts and ticks.** `not_ready_timeout_hours` (168 by default, reason `not_ready_timeout_expired`) cancels the items that never became mergeable; `testing_timeout_minutes` bounds a run. The reconciler also runs on a 30 s tick for each queue that has live items: it rereads the checks of a run in progress through the API when the run has been silent for 5 minutes, rereads the state of each live PR every 5 minutes (which catches up the lost `closed`, `synchronize` and merge events), and rechecks the mergeability of `not_ready` items with a progressive per-item delay of 1 to 15 minutes, in one GraphQL request grouped per repository: a lost webhook thus only delays the queue, never blocks it.
