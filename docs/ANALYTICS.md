# Analytics: Postgres first, ClickHouse later

Analytics goes through a single trait, `AnalyticsStore` (`cihub-analytics`), with two implementations: Postgres, the only one shipped in v1 and sufficient up to a few million events per month, and ClickHouse, enabled by configuration when the volume or the depth of history justifies it. The notifier feeds one or the other from the outbox, the modules see only the interface, and the dashboard asks its questions to the interface. Moving from one to the other is a data migration, not a change of application code.

In v1, the Postgres implementation derives four fact tables from the event stream, partitioned by month and indexed by (`org_id`, `queue_id`, date): `an_item_conclusions` (one row per concluded item, with its wait, test and stay durations), `an_state_durations` (one row per pass through a state), `an_test_run_results` (one row per run) and `an_hourly_queue_stats` (hourly aggregate recomputed by a job every five minutes for the current hour and the previous one). Percentiles are computed with `percentile_cont` on the fact tables for short ranges and on approximate quantiles stored in the aggregate for long ranges. The ClickHouse schema below is the equivalent target, column for column, so that the migration is a copy.

In both implementations, the notifier writes only from the outbox and the derived tables are built from the same event (a terminal transition carries the whole timeline of the item in `payload`), so they are exact rather than reconstructed by join. With Postgres, the write of the facts and the marking of the outbox are in the same transaction: exactly-once is free. With ClickHouse, the notifier reserves a deterministic batch (`batch_id`, up to 1,000 rows or 2 s), inserts it with `insert_deduplication_token = batch_id` so that a recovery after a crash is discarded rather than counted twice, marks the batch done only after acknowledgment, and the queries read the `ReplacingMergeTree` tables with `FINAL` or `argMax` because the replacement is deferred.

Questions the schema answers directly, each matching a chart of the dashboard or an API call:

- Number of conclusions per day and per queue, broken down by reason (histogram of the Health view; `item_conclusions`).
- Time in queue p50/p95/p99 per day or per hour (curve of the Health view; `quantileExact` on `item_conclusions`, or the aggregate for ranges beyond 30 days).
- Test duration and CI runs triggered per PR (`test_run_results`), including the share of bisection.
- Restart rate and its causes (`state_durations` whose `exit_reason` is a restart reason), the first thing to look at when a queue seems slow.
- Throughput per impacted target in parallel mode (`arrayJoin(impacted_targets)`).
- Detail of the PRs behind each bar (capped at 2,500 rows).

The Prometheus endpoint (`GET /api/v1/metrics`) is served from Postgres: instant gauges (`mq_depth_current`, `mq_awaiting_mergeability`, `mq_testing_slots_active`, `mq_prs_testing`) from the live tables, sliding windows (`mq_pr_conclusions_1h_total`, `mq_pr_restarts_1h_total`, `mq_pr_state_duration_1h_seconds{state}` and the histograms of wait, test and time in queue with the buckets 60, 300, 600, 900, 1800, 3600, 5400, 7200 s) from the fact tables, labeled by `repo`, `branch` and `queue_type` (`main`, `bisection`). The totals are also exposed as true counters (`mq_pr_conclusions_total`), so that `rate()` works.

Retention with Postgres: 90 days for `events`, 13 months for the fact tables, unlimited for the hourly aggregate; the oldest partitions are detached by a daily job. With ClickHouse: 13 months for `events`, unlimited for the aggregates, one replica per instance with `ReplicatedMergeTree` as soon as a second node exists. In both cases, the query layer applies the same isolation by `org_id` as the rest of the database.
