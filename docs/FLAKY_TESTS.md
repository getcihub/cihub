# Test results and flaky tests

The `flakytests` module receives the test results of the CI in OTLP format, where each test case is a span, keeps their history per repository, and classifies each case as stable, suspect, flaky or broken. The merge queue asks it, through a contract, at the only moment when it designates a culprit: if all the failing checks are explained by tests known as flaky, it restarts once instead of evicting the PR.

**Reception.** CIHub exposes a standard OTLP/HTTP receiver on `POST /api/v1/otlp/v1/traces` (protobuf or JSON), authenticated by organization token or by GitHub Actions run identifier for forks. A CI job sends its results there with any OpenTelemetry SDK or collector, which reuses an existing ecosystem rather than a homemade format. For toolchains that produce only JUnit XML, a converter is provided in two forms: the command `cihub test-results push --junit reports/*.xml` and the GitHub action `cihub/upload-test-results`, which read the XML and send it as spans. The model follows the OpenTelemetry semantic conventions for tests (`test.case.name`, `test.suite.name`, `test.case.result.status`) extended with context attributes that the converter and the action fill in: `vcs.repository.name`, `vcs.ref.head.revision`, `vcs.ref.head.name`, `cicd.pipeline.run.id`, `cicd.pipeline.task.name`, and `cihub.test_run_id` when the run comes from the queue.

| OTLP level  | What it represents                | Key attributes                                                                                                                                                          |
| ----------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trace       | One CI run on a commit            | `vcs.repository.name`, `vcs.ref.head.revision`, `cicd.pipeline.run.id`                                                                                                  |
| Root span   | A job or a test shard             | `cicd.pipeline.task.name`, `test.framework`, `host.name`                                                                                                                |
| Suite span  | A suite or a test file            | `test.suite.name`                                                                                                                                                       |
| Case span   | A test case, with its duration    | `test.case.name`, `test.case.result.status` (`pass`, `fail`, `skip`, `error`), `test.case.retry` (attempt number), error message and stack trace as span events         |

**Storage.** The case spans are flattened in Postgres into a fact table `ft_results` partitioned by month (`org_id`, `repo_id`, `sha`, `branch`, `run_id`, `case_key`, `status`, `attempt`, `duration_ms`, `error_fingerprint`, `observed_at`), with `case_key` = stable hash of (suite, name, parameters). A table `ft_cases` carries the current state per case and per repository (`state`, sliding failure rate over 7 and 30 days, last flip, owner, `quarantined_at`), recomputed by a job at each ingestion. The raw OTLP payload is kept 7 days for replay. These tables move to ClickHouse through the same `AnalyticsStore` trait (`cihub-analytics`) as the rest, when it is enabled.

**Detection.** A case is judged on three signals, from the strongest to the weakest: (1) on the same commit, different outcomes between two runs or between two attempts of the same run; (2) on the target branch, supposed green, a pass/fail flip without a change of the test code; (3) in the queue, a failure then a success for the same subset of code during a bisection, a signal that CIHub exploits. The thresholds (`flaky` from 2 flips over 7 days or a failure rate between 5 and 80 % on the target, `broken` beyond, `suspect` at the first flip) are repository settings. Quarantine is manual by default, automatic as an option; it never modifies the customer's CI, it only changes how the queue reads it.

**What the queue does with it.** The `FlakeOracle` trait (`cihub-contracts`) receives the failing checks of a run and answers from `ft_cases` in less than 50 ms: `AllFailuresAreKnownFlakes`, the list of the incriminated cases and a confidence. A positive answer is worth a single restart (`tests_restarted_flake_suspected`, `DECISIONS.md` Q1); a second failure follows the normal path. Without the module, the neutral oracle answers "unknown" and the queue behaves exactly as [ALGORITHMS.md](ALGORITHMS.md) describes. In the other direction, the module subscribes to `mergequeue.run.completed` (`DECISIONS.md` Q12) to attach the results to the queue runs and to the bisections.

**Surfaces.** `GET /api/v1/flaky/cases` (filters repository, state, owner, sort by cost = failures × duration), `GET /api/v1/flaky/cases/{key}` with the history, `POST /api/v1/flaky/cases/{key}/quarantine` and `unquarantine`, `GET /api/v1/flaky/runs/{run_id}`; a "Flaky tests" page per repository, a badge on the page of a queue run, an optional comment on the PR listing the flaky tests encountered, and the webhooks `flaky.case.state_changed` and `flaky.case.quarantined`.
