# Résultats de tests et tests instables

Contexte : qui touche au module `flakytests`, au récepteur OTLP, au convertisseur JUnit ou au trait `FlakeOracle`. Le code est la source de vérité (`AGENTS.md` D1) ; ce fichier dit l'intention.

Le module `flakytests` reçoit les résultats de tests de la CI au format OTLP, où chaque cas de test est un span, en garde l'historique par dépôt, et classe chaque cas comme stable, suspect, instable ou cassé. La file de merge l'interroge, par un contrat, au seul moment où elle désigne un coupable : si tous les checks en échec s'expliquent par des tests connus comme instables, elle relance une fois au lieu d'évincer la PR.

**Réception.** CIHub expose un récepteur OTLP/HTTP standard sur `POST /api/v1/otlp/v1/traces` (protobuf ou JSON), authentifié par jeton d'organisation ou par identifiant d'exécution GitHub Actions pour les forks. Un job de CI y envoie ses résultats avec n'importe quel SDK ou collecteur OpenTelemetry, ce qui réutilise un écosystème existant plutôt qu'un format maison. Pour les chaînes qui ne produisent que du JUnit XML, un convertisseur est fourni sous deux formes : la commande `cihub test-results push --junit reports/*.xml` et l'action GitHub `cihub/upload-test-results`, qui lisent le XML et l'envoient comme spans. Le modèle suit les conventions sémantiques OpenTelemetry pour les tests (`test.case.name`, `test.suite.name`, `test.case.result.status`) complétées d'attributs de contexte que le convertisseur et l'action renseignent : `vcs.repository.name`, `vcs.ref.head.revision`, `vcs.ref.head.name`, `cicd.pipeline.run.id`, `cicd.pipeline.task.name`, et `cihub.test_run_id` quand l'exécution vient de la file.

| Niveau OTLP | Ce qu'il représente               | Attributs clés                                                                                                                                                          |
| ----------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trace       | Une exécution de CI sur un commit | `vcs.repository.name`, `vcs.ref.head.revision`, `cicd.pipeline.run.id`                                                                                                  |
| Span racine | Un job ou un shard de tests       | `cicd.pipeline.task.name`, `test.framework`, `host.name`                                                                                                                |
| Span suite  | Une suite ou un fichier de tests  | `test.suite.name`                                                                                                                                                       |
| Span cas    | Un cas de test, avec sa durée     | `test.case.name`, `test.case.result.status` (`pass`, `fail`, `skip`, `error`), `test.case.retry` (numéro de tentative), message et trace d'erreur en événements de span |

**Stockage.** Les spans de cas sont aplatis dans Postgres en une table de faits `ft_results` partitionnée par mois (`org_id`, `repo_id`, `sha`, `branch`, `run_id`, `case_key`, `status`, `attempt`, `duration_ms`, `error_fingerprint`, `observed_at`), avec `case_key` = hachage stable de (suite, nom, paramètres). Une table `ft_cases` porte l'état courant par cas et par dépôt (`state`, taux d'échec glissant sur 7 et 30 jours, dernière alternance, propriétaire, `quarantined_at`), recalculée par un job à chaque ingestion. Le payload OTLP brut est conservé 7 jours pour rejeu. Ces tables passent sur ClickHouse par le même trait `AnalyticsStore` (`cihub-analytics`) que le reste, quand il est activé.

**Détection.** Un cas est jugé sur trois signaux, du plus sûr au plus faible : (1) sur un même commit, des issues différentes entre deux exécutions ou entre deux tentatives d'une même exécution ; (2) sur la branche cible, censée verte, une alternance succès/échec sans changement du code du test ; (3) dans la file, un échec puis un succès pour le même sous-ensemble de code au cours d'une bissection, signal que Trunk laisse de côté et que CIHub exploite. Les seuils (`flaky` à partir de 2 alternances sur 7 jours ou d'un taux d'échec entre 5 et 80 % sur la cible, `broken` au-delà, `suspect` à la première alternance) sont des réglages de dépôt. La quarantaine est manuelle par défaut, automatique en option ; elle ne modifie jamais la CI du client, elle change seulement la lecture qu'en fait la file.

**Ce que la file en fait.** Le trait `FlakeOracle` (`cihub-contracts`) reçoit les checks en échec d'une exécution et répond depuis `ft_cases` en moins de 50 ms : `AllFailuresAreKnownFlakes`, la liste des cas incriminés et une confiance. Une réponse positive vaut une seule relance (`tests_restarted_flake_suspected`, `AGENTS.md` Q1) ; une seconde échec suit le chemin normal. Sans le module, l'oracle neutre répond « inconnu » et la file se comporte exactement comme le décrit [ALGORITHMS.md](ALGORITHMS.md). Dans l'autre sens, le module s'abonne à `mergequeue.run.completed` (`AGENTS.md` Q12) pour rattacher les résultats aux exécutions de file et aux bissections.

**Surfaces.** `GET /api/v1/flaky/cases` (filtres dépôt, état, propriétaire, tri par coût = échecs × durée), `GET /api/v1/flaky/cases/{key}` avec l'historique, `POST /api/v1/flaky/cases/{key}/quarantine` et `unquarantine`, `GET /api/v1/flaky/runs/{run_id}` ; une page « Tests instables » par dépôt, un badge sur la page d'une exécution de file, un commentaire optionnel sur la PR listant les tests instables rencontrés, et les webhooks `flaky.case.state_changed` et `flaky.case.quarantined`.
