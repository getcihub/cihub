# Intégration GitHub

Contexte : qui touche à `cihub-github`, aux permissions de l'App, aux webhooks, à la mergeabilité, aux commandes ou aux surfaces sur la PR. Le code est la source de vérité (`AGENTS.md` D1) ; ce fichier dit l'intention.

CIHub se présente comme une GitHub App (`cihub-io`) installée par organisation, avec une seconde App optionnelle (`cihub-sudo`) qui porte le contournement des protections de branche pour les merges direct-to-queue, pour que l'App principale n'ait jamais besoin de droits d'administration. Toute l'authentification passe par des jetons d'installation émis depuis la clé privée de l'App et mis en cache jusqu'à 5 minutes avant expiration.

| Permission      | Niveau            | Usage                                                                                                                                 |
| --------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Contents        | write             | créer et supprimer les refs `cihub-temp/**` et `cihub-merge/**`, API merges, lire `.cihub.yaml` ou `.cihub.yml`                                 |
| Pull requests   | write             | lire l'état et la mergeabilité des PR, ouvrir et fermer les PR brouillons de test, merger les PR, poster et modifier les commentaires |
| Commit statuses | write             | publier le statut `CIHub Merge Queue (<branch>)`                                                                                      |
| Checks          | read              | observer les check runs sur les SHA de test                                                                                           |
| Metadata        | read              | lister les dépôts                                                                                                                     |
| Administration  | read              | lire les protections de branche et les rulesets pour déduire les checks requis et faire tourner le vérificateur de configuration      |
| Issues          | write             | labels sur les PR (label d'entrée, labels d'état)                                                                                     |
| Members         | read              | associer les logins GitHub aux rôles de l'organisation pour les commandes réservées aux admins                                        |
| Actions         | write (optionnel) | annuler les workflows des branches de test remplacées et relancer les seuls jobs en échec ; à cocher à la main seulement pour ces actions (`AGENTS.md` D72, D92) |

Événements webhook souscrits : `installation`, `installation_repositories`, `pull_request` (opened, synchronize, closed, reopened, edited, converted\_to\_draft, ready\_for\_review, labeled, unlabeled), `pull_request_review`, `issue_comment` (commandes), `push` (branches cibles et têtes de PR), `check_run`, `check_suite`, `status`, `branch_protection_rule`, `repository` (renommé, supprimé). Chaque livraison est vérifiée avec le secret HMAC, dédoublonnée par `X-GitHub-Delivery`, stockée et acquittée en moins de 2 s ; le traitement est asynchrone.

La mergeabilité est lue, jamais calculée. Les jobs `refresh_prs` et `submit_pr` demandent à GraphQL `pullRequest.mergeable`, `mergeStateStatus` (`CLEAN`, `BLOCKED`, `BEHIND`, `DIRTY`, `DRAFT`, `UNSTABLE`, `HAS_HOOKS`, `UNKNOWN`), `reviewDecision`, `statusCheckRollup`, le titre et le corps de la PR (pour le titre du commit de merge, `AGENTS.md` D126), et pour les `queue_conditions` (D143) `headRefName`, `isCrossRepository`, `createdAt`, `latestOpinionatedReviews` et `reviewRequests` (un utilisateur ou une équipe `<org>/<équipe>`), en une requête pour jusqu'à 50 PR par dépôt. Les fichiers modifiés (REST, 3 000 au plus) et les fils de revue non résolus (GraphQL, les 100 premiers) sont lus à part, seulement quand une condition de la file les utilise. Le merge direct compare la tête de la cible et celle de la PR par l'API *compare* (`ahead` ou `identical`, `AGENTS.md` D153). L'adaptateur traduit `mergeStateStatus` en `Mergeability` (`AGENTS.md` D23) : `CLEAN`, `HAS_HOOKS` et `UNSTABLE` (un check non requis a échoué) donnent `mergeable` et admettent l'entrée, conformément à la sémantique des protections de branche ; `BEHIND` donne `behind`, `DIRTY` donne `conflict`, `BLOCKED` et `DRAFT` donnent `blocked`, `UNKNOWN` donne `unknown`. Il traduit aussi un check run en `CheckKind` `check`, un statut de commit en `status`, et la suspension ou la suppression de l'installation en fait `access.lost`. `unknown` programme une relecture après un court délai, car GitHub calcule cette valeur paresseusement, et produit entre-temps une raison de blocage `undetermined` ; tout le reste maintient l'entrée en `not_ready` avec la liste `block_reasons[]` rendue dans le commentaire de la PR. Pour une PR `blocked`, `pr.observed` porte les checks que les règles de la branche exigent, et la raison nomme le check requis en échec (`failing_required_check`) ou pas encore conclu (`awaiting_required_check`) ; `undetermined` reste quand aucun check requis ne l'explique (`AGENTS.md` D158). Une exception est calculée par ces jobs (`AGENTS.md` D105) : quand le seul check requis non satisfait est le contexte `CIHub Merge Queue (<branch>)` de la file elle-même, et qu'aucune revue ne manque, la PR est rapportée `mergeable` et l'entrée est admise, sans quoi un dépôt qui exige le statut de la file ne pourrait jamais entrer dans la file. Les revérifications sont pilotées par les événements (revues, check runs et statuts sur la tête de la PR, `synchronize`, pushes sur la cible qui rendent des PR `BEHIND`), le sondage progressif du tic servant de filet, ce qui maintient un dépôt de 50 PR en attente sous 300 points GraphQL par heure.

La file écrit trois choses sur la PR. Un **statut de commit** nommé `CIHub Merge Queue (<branche cible>)` sur la tête de la PR : `pending` tant que l'entrée est en `not_ready`, `pending`, `testing` ou `pending_failure`, `success` à partir de `tests_passed` (posé avant l'appel de merge, pour que la règle de check requis de GitHub soit satisfaite quand la file merge), `failure` sur `failed` et `error` sur `cancelled`, sans URL de détails avant le tableau de bord (lot 10, `AGENTS.md` D156). Les équipes peuvent en faire un check requis pour que rien ne merge sans test vérifié par la file ; c'est le ruleset de restriction de push décrit plus bas qui empêche réellement de merger en contournant la file. Un **commentaire de bot** par PR, posé à l'ouverture de la PR sur une branche gérée (le commentaire d'accueil, avec une case de soumission, `AGENTS.md` D163) ou à la soumission, puis modifié sur place à chaque changement d'état, en anglais, montrant l'état, la position, les prédécesseurs, le nom de la branche de test, les raisons de blocage et, en cas d'échec, les checks en échec ; il dit d'écrire `/cihub restart` pour une entrée en test et `/cihub merge` pour une entrée terminée. La réconciliation écrit le rendu voulu dans `pr_surfaces`, et le job `publish_surfaces` le publie (`AGENTS.md` D156). Des **labels d'état** optionnels `cihub:queued`, `cihub:testing`, `cihub:failed`, qui continuent d'être mis à jour sur une PR qui les porte déjà même après désactivation du réglage.

Les commandes sont lues dans les événements `issue_comment` des PR : `/cihub merge [--priority=urgent|high|medium|low|0-255] [--no-batch] [--direct] [--queue=<nom>]`, `/cihub cancel`, `/cihub restart` ; aucune commande d'un autre produit n'est acceptée (`AGENTS.md` D139). L'auteur du commentaire doit avoir le droit `write` sur le dépôt (`--direct` exige `admin`), vérifié via l'API de permissions des collaborateurs et mis en cache 5 minutes. Un commentaire ne donne pas la branche de base de la PR : il passe par la connexion, et le job `submit_pr` vérifie la permission, lit la PR, puis donne la soumission à la file de sa branche de base (`AGENTS.md` D102, D103). Le label de soumission (`enqueue_label`) soumet la PR quand une livraison dit qu'il a été posé ; le job vérifie que la PR le porte encore. La case du commentaire de CIHub soumet aussi la PR : l'adaptateur traduit un `issue_comment.edited` où la case `<!-- cihub:submit -->` passe de vide à cochée, par un autre auteur que le bot, et la soumission suit le chemin de `/cihub merge` (permission `write` de l'auteur) si le commentaire est celui de `pr_comments` (D163). `/cihub cancel` et `/cihub restart` passent par le job `pr_command`, qui trouve l'entrée vivante de la PR ; `restart` ne vaut que pour une entrée en test. Une commande refusée reçoit un commentaire qui dit pourquoi (`AGENTS.md` D157).

Attentes de protection de branche, documentées pour les clients : deux rulesets sur la branche cible, l'un restreignant les mises à jour avec l'App `cihub-io` en liste de contournement en mode **exempt** (le mode `always` de GitHub ne couvre pas les mises à jour de branche par une App, et le vérificateur de configuration le contrôle empiriquement par une mise à jour de ref sans effet), l'autre portant les règles de mergeabilité sans aucun contournement ; tout autre ruleset doit exclure `cihub-temp/**/*` et `cihub-merge/**/*` ; « exiger que les branches soient à jour » doit être désactivé, sauf si l'on s'appuie sur le merge direct sur main. Le vérificateur de configuration (`GET /api/v1/queues/{id}/config-check`, `AGENTS.md` D162) lit les rulesets de la branche cible et des branches de test et signale chacun de ces points par un constat (`update_restriction_missing`, `app_not_exempt`, `test_branches_not_excluded`, `up_to_date_required`) ; la mise à jour de ref sans effet attend une décision, et le tableau de bord l'affichera (lot 10).

**Création de l'App** (`AGENTS.md` D92). L'opérateur crée l'App à la main, dans les réglages GitHub de son organisation (*Settings → Developer settings → GitHub Apps → New GitHub App*) ou de son compte :

1. Nom au choix, et URL de la page d'accueil : l'adresse de l'instance.
2. *Webhook* actif, avec l'URL `<adresse publique de CIHub>/webhooks/github` et un secret aléatoire (par exemple `openssl rand -hex 32`).
3. Les permissions du tableau ci-dessus ; `Actions: write` seulement pour annuler et relancer la CI.
4. Les événements de la liste ci-dessus (`installation` et `installation_repositories` arrivent sans abonnement).
5. *Where can this GitHub App be installed?* : *Only on this account*, sauf pour servir plusieurs comptes.
6. Après la création : noter l'*App ID* et générer une clé privée (fichier `.pem`).

Le serveur reçoit ensuite `CIHUB_GITHUB_APP_ID`, `CIHUB_GITHUB_PRIVATE_KEY_FILE` (ou `CIHUB_GITHUB_PRIVATE_KEY`), `CIHUB_GITHUB_WEBHOOK_SECRET` et, pour un GitHub Enterprise Server, `CIHUB_GITHUB_URL` (`docs/DEPLOYMENT.md`). Sans elles, `cihub-server` s'arrête au démarrage avec un message qui les nomme. Enfin, l'opérateur installe l'App sur les dépôts à servir (*Install App*). Une App qui existe déjà convient, si ses permissions, ses événements et son URL de webhook sont ceux-ci.

**Réception et routage.** `POST /webhooks/github` vérifie la signature, stocke la livraison sans la router et répond `202` (D83, D84). La boucle de routage du rôle `web` traduit la livraison en événement neutre (`ScmDelivery`), trouve la connexion par `installation.id`, et trouve la file seulement quand une seule est sûre : une PR par sa branche de base, un push par sa branche (D85). Un check est routé vers sa file par le nom de sa branche de test, qui porte l'identifiant de son exécution, ou par son SHA de test une fois la branche supprimée (`docs/CI.md`, `AGENTS.md` D118) ; un check d'une autre branche va à sa connexion seulement. Une livraison d'une installation inconnue reste sans organisation (D86). Un job `sweep_deliveries` redemande toutes les 5 minutes les livraisons que GitHub a tenté d'envoyer et que l'inbox n'a pas (D88).

L'embarquement commence dans le tableau de bord, pas sur GitHub : l'utilisateur se connecte avec GitHub, crée ou rejoint l'organisation CIHub correspondant à son organisation GitHub, et installe l'App depuis là avec un paramètre `state` qui lie l'installation obtenue à cette organisation ; un webhook `installation.created` sans `state` correspondant est stocké comme non réclamé et présenté à tout admin de cette organisation GitHub à sa prochaine connexion. Sans tableau de bord, `cihub-server admin bootstrap --installation <id>` relie une installation à une nouvelle organisation (`AGENTS.md` D154, `docs/DEPLOYMENT.md`) ; le job `sync_repos` lit ensuite les dépôts de l'installation, à chaque livraison `installation_repositories` et toutes les heures (D155). Une organisation peut porter plusieurs installations (l'App principale, l'App sudo et les installations sur comptes personnels), et seuls les admins d'organisation peuvent créer des files.
