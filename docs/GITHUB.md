# GitHub integration

CIHub presents itself as a GitHub App (`cihub-io`) installed per organization, with an optional second App (`cihub-sudo`) that carries the branch protection bypass for direct-to-queue merges, so that the main App never needs administration rights. All authentication goes through installation tokens issued from the App's private key and cached until 5 minutes before expiry.

| Permission      | Level             | Usage                                                                                                                                 |
| --------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Contents        | write             | create and delete the `cihub-temp/**` and `cihub-merge/**` refs, merges API, read `.cihub.yaml` or `.cihub.yml`                       |
| Pull requests   | write             | read the state and mergeability of PRs, open and close the test draft PRs, merge PRs, post and edit comments                          |
| Commit statuses | write             | publish the `CIHub Merge Queue (<branch>)` status                                                                                     |
| Checks          | read              | observe the check runs on the test SHAs                                                                                               |
| Metadata        | read              | list the repositories                                                                                                                 |
| Administration  | read              | read the branch protections and rulesets to derive the required checks and run the configuration checker                              |
| Issues          | write             | labels on PRs (enqueue label, state labels), reactions on the command comments                                                        |
| Members         | read              | map GitHub logins to organization roles for admin-only commands                                                                       |
| Actions         | write (optional)  | cancel the workflows of superseded test branches and restart only the failed jobs; check it by hand only for these actions (`DECISIONS.md` D72, D92) |

Subscribed webhook events: `installation`, `installation_repositories`, `pull_request` (opened, synchronize, closed, reopened, edited, converted\_to\_draft, ready\_for\_review, labeled, unlabeled), `pull_request_review`, `issue_comment` (commands), `push` (target branches and PR heads), `check_run`, `check_suite`, `status`, `branch_protection_rule`, `repository` (renamed, deleted). Each delivery is verified with the HMAC secret, deduplicated by `X-GitHub-Delivery`, stored and acknowledged in under 2 s; processing is asynchronous.

Mergeability is read, never computed. The `refresh_prs` and `submit_pr` jobs ask GraphQL for `pullRequest.mergeable`, `mergeStateStatus` (`CLEAN`, `BLOCKED`, `BEHIND`, `DIRTY`, `DRAFT`, `UNSTABLE`, `HAS_HOOKS`, `UNKNOWN`), `reviewDecision`, `statusCheckRollup`, the title and body of the PR (for the merge commit title, `DECISIONS.md` D126), and for the `queue_conditions` (D143) `headRefName`, `isCrossRepository`, `createdAt`, `latestOpinionatedReviews` and `reviewRequests` (a user or a team `<org>/<team>`), in one request for up to 50 PRs per repository. The changed files (REST, 3,000 at most) and the unresolved review threads (GraphQL, the first 100) are read separately, only when a queue condition uses them. The direct merge compares the head of the target and that of the PR through the *compare* API (`ahead` or `identical`, `DECISIONS.md` D153). The adapter translates `mergeStateStatus` into `Mergeability` (`DECISIONS.md` D23): `CLEAN`, `HAS_HOOKS` and `UNSTABLE` (a non-required check failed) give `mergeable` and admit the item, in line with the semantics of branch protections; `BEHIND` gives `behind`, `DIRTY` gives `conflict`, `BLOCKED` and `DRAFT` give `blocked`, `UNKNOWN` gives `unknown`. It also translates a check run into `CheckKind` `check`, a commit status into `status`, and the suspension or removal of the installation into an `access.lost` fact. `unknown` schedules a re-read after a short delay, because GitHub computes this value lazily, and produces an `undetermined` block reason in the meantime; everything else keeps the item in `not_ready` with the `block_reasons[]` list rendered in the PR comment. For a `blocked` PR, `pr.observed` carries the checks that the branch rules require, and the reason names the required check that fails (`failing_required_check`) or has not concluded yet (`awaiting_required_check`); `undetermined` remains when no required check explains it (`DECISIONS.md` D158). One exception is computed by these jobs (`DECISIONS.md` D105): when the only unsatisfied required check is the `CIHub Merge Queue (<branch>)` context of the queue itself, and no review is missing, the PR is reported `mergeable` and the item is admitted; otherwise a repository that requires the queue status could never enter the queue. Re-checks are driven by events (reviews, check runs and statuses on the PR head, `synchronize`, pushes on the target that make PRs `BEHIND`), with the progressive polling of the tick as a safety net, which keeps a repository with 50 waiting PRs under 300 GraphQL points per hour.

The queue writes three things on the PR. A **commit status** named `CIHub Merge Queue (<target branch>)` on the PR head: `pending` while the item is `not_ready`, `pending`, `testing` or `pending_failure`, `success` from `tests_passed` on (set before the merge call, so that GitHub's required check rule is satisfied when the queue merges), `failure` on `failed` and `error` on `cancelled`, without a details URL before the dashboard (Lot 10, `DECISIONS.md` D156). Teams can make it a required check so that nothing merges without a test verified by the queue; the push restriction ruleset described below is what really prevents a merge that bypasses the queue. One **bot comment** per PR, posted when the PR is opened on a managed branch (the welcome comment, with a submission checkbox, `DECISIONS.md` D163) or at submission, then edited in place at each state change, in English, showing the state, the position, the predecessors, the test branch name, the block reasons and, on failure, the failing checks; it says to write `/cihub restart` for an item under test and `/cihub merge` for a finished item. The reconciliation writes the desired rendering in `pr_surfaces`, and the `publish_surfaces` job publishes it (`DECISIONS.md` D156). Optional **state labels** `cihub:queued`, `cihub:testing`, `cihub:failed`, which keep being updated on a PR that already carries them even after the setting is disabled.

Commands are read from the `issue_comment` events of PRs: `/cihub merge [--priority=urgent|high|medium|low|0-255] [--no-batch] [--direct] [--queue=<name>]`, `/cihub cancel`, `/cihub restart`; no command from another product is accepted (`DECISIONS.md` D139). The comment author must have the `write` permission on the repository (`--direct` requires `admin`), verified through the collaborators permission API and cached for 5 minutes. A comment does not give the base branch of the PR: it goes through the connection, and the `submit_pr` job verifies the permission, reads the PR, then gives the submission to the queue of its base branch (`DECISIONS.md` D102, D103). The submission label (`enqueue_label`) submits the PR when a delivery says it was added; the job verifies that the PR still carries it. The checkbox of CIHub's comment also submits the PR: the adapter translates an `issue_comment.edited` where the `<!-- cihub:submit -->` checkbox goes from empty to checked, by an author other than the bot, and the submission follows the `/cihub merge` path (`write` permission of the author) if the comment is the one in `pr_comments` (D163). `/cihub cancel` and `/cihub restart` go through the `pr_command` job, which finds the live item of the PR; `restart` only applies to an item under test. A refused command receives a comment that says why (`DECISIONS.md` D157). A command that its job accepts receives a `+1` reaction on its comment once the queue has it; a failed reaction is logged and does not fail the job (`DECISIONS.md` D166).

Branch protection expectations, documented for customers: two rulesets on the target branch, one that restricts updates with the `cihub-io` App in the bypass list in **exempt** mode (GitHub's `always` mode does not cover branch updates by an App, and the configuration checker verifies it empirically with a no-op ref update), the other that carries the mergeability rules without any bypass; any other ruleset must exclude `cihub-temp/**/*` and `cihub-merge/**/*`; "require branches to be up to date" must be disabled, unless you rely on the direct merge on main. The configuration checker (`GET /api/v1/queues/{id}/config-check`, `DECISIONS.md` D162) reads the rulesets of the target branch and of the test branches and reports each of these points as a finding (`update_restriction_missing`, `app_not_exempt`, `test_branches_not_excluded`, `up_to_date_required`); the no-op ref update awaits a decision, and the dashboard will display it (Lot 10).

**Creating the App** (`DECISIONS.md` D92). The operator creates the App by hand, in the GitHub settings of their organization (*Settings → Developer settings → GitHub Apps → New GitHub App*) or of their account:

1. Any name, and homepage URL: the address of the instance.
2. *Webhook* active, with the URL `<CIHub public address>/webhooks/github` and a random secret (for example `openssl rand -hex 32`).
3. The permissions of the table above; `Actions: write` only to cancel and restart the CI.
4. The events of the list above (`installation` and `installation_repositories` arrive without subscription).
5. *Where can this GitHub App be installed?*: *Only on this account*, unless it serves several accounts.
6. After creation: note the *App ID* and generate a private key (`.pem` file).

The server then receives `CIHUB_GITHUB_APP_ID`, `CIHUB_GITHUB_PRIVATE_KEY_FILE` (or `CIHUB_GITHUB_PRIVATE_KEY`), `CIHUB_GITHUB_WEBHOOK_SECRET` and, for a GitHub Enterprise Server, `CIHUB_GITHUB_URL` (`docs/DEPLOYMENT.md`). Without them, `cihub-server` stops at startup with a message that names them. Finally, the operator installs the App on the repositories to serve (*Install App*). An App that already exists is suitable, if its permissions, its events and its webhook URL are these.

**Reception and routing.** `POST /webhooks/github` verifies the signature, stores the delivery without routing it and responds `202` (D83, D84). The routing loop of the `web` role translates the delivery into a neutral event (`ScmDelivery`), finds the connection by `installation.id`, and finds the queue only when a single one is certain: a PR by its base branch, a push by its branch (D85). A check is routed to its queue by the name of its test branch, which carries the identifier of its run, or by its test SHA once the branch is deleted (`docs/CI.md`, `DECISIONS.md` D118); a check from another branch goes to its connection only. A delivery from an unknown installation stays without an organization (D86). A `sweep_deliveries` job re-requests every 5 minutes the deliveries that GitHub tried to send and that the inbox does not have (D88).

Onboarding starts in the dashboard, not on GitHub: the user signs in with GitHub, creates or joins the CIHub organization that corresponds to their GitHub organization, and installs the App from there with a `state` parameter that ties the resulting installation to that organization; an `installation.created` webhook without a matching `state` is stored as unclaimed and presented to any admin of that GitHub organization at their next sign-in. Without the dashboard, `cihub-server admin bootstrap --installation <id>` links an installation to a new organization (`DECISIONS.md` D154, `docs/DEPLOYMENT.md`); the `sync_repos` job then reads the repositories of the installation, at each `installation_repositories` delivery and every hour (D155). An organization can carry several installations (the main App, the sudo App and the installations on personal accounts), and only organization admins can create queues.
