# Fiabilité et gestion des pannes

Contexte : qui touche à un job, à un appel GitHub, au réconciliateur ou à la boucle de réparation : chaque panne a une détection et un traitement nommés ici. Le code est la source de vérité (`AGENTS.md` D1) ; ce fichier dit l'intention.

La promesse de correction de la file est qu'une PR n'est mergée qu'après une exécution de test réussie sur un commit dont l'arbre égale ce que contiendra la branche cible ; la promesse de résilience est qu'aucune intention n'est jamais perdue : une soumission, une commande, un résultat de check survivent aux crashes, aux webhooks perdus, aux pannes de GitHub et aux opérateurs concurrents, et sont au pire retardés. Les mécanismes sont le journal d'événements, la convergence idempotente vers un état voulu, la boucle de réparation, le budget du SCM ordonnancé, et des modes dégradés explicites plutôt que des comportements implicites sous stress.

| Panne                                                               | Détection                                                                                                                                                                                                                                                                    | Traitement                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Crash du scheduler pendant une réconciliation                       | La transaction est annulée ; le verrou de transaction est libéré                                                                                                                                                                                                             | La réplique suivante rejoue la réconciliation depuis le même état ; aucune écriture partielle n'existe                                                                                                                                                 |
| Crash d'un worker pendant un job                                    | `locked_until` expire                                                                                                                                                                                                                                                        | Le job est repris ; chaque exécuteur lit d'abord GitHub (la branche existe-t-elle ? la PR est-elle mergée ? le commentaire existe-t-il ?) et saute les étapes déjà faites via l'`idempotency_key` de chaque étape                                      |
| Webhook GitHub perdu (GitHub ne réessaie pas une livraison échouée) | L'insertion en inbox précède tout traitement et répond en moins de 2 s ; un balayage toutes les 5 minutes (job `sweep_deliveries`, `AGENTS.md` D88) liste les tentatives des 10 dernières minutes via `GET /app/hook/deliveries` et redemande celles absentes de l'inbox ; le tic relit les PR vivantes et les exécutions silencieuses | Un retard d'au plus un balayage ou un tic, jamais une transition perdue                                                                                                                                                                                |
| Webhooks désordonnés                                                | `received_at` et horodatages GitHub                                                                                                                                                                                                                                          | Traitement séquentiel par file ; un `check_run` pour un SHA qu'aucune exécution n'attend est stocké puis ignoré                                                                                                                                        |
| Livraison de webhook en double                                      | `X-GitHub-Delivery` unique dans `webhook_inbox`                                                                                                                                                                                                                              | La seconde insertion est sans effet                                                                                                                                                                                                                    |
| 5xx GitHub au merge                                                 | Code HTTP                                                                                                                                                                                                                                                                    | Le job `merge_pr` refait l'appel avec le backoff, puis donne `merge_repeated_server_errors` après 6 tentatives, environ 60 s (`AGENTS.md` D123)                                                                                                  |
| 405 GitHub « merge already in progress »                            | Code HTTP                                                                                                                                                                                                                                                                    | Reprise avec backoff ; avant d'abandonner, lire la PR : mergée = succès, ouverte et sur la base = fermer sans resoumettre, sinon `merge_already_in_progress`                                                                                |
| 409 au merge (`sha` différent)                                      | Code HTTP                                                                                                                                                                                                                                                                    | `pr_updated_at_merge_time` ; l'entrée échoue, l'utilisateur resoumet                                                                                                                                                                                   |
| PR mergée hors de la file                                           | Le job `merge_pr` lit la PR avant de la merger                                                                                                                                                                                                                       | `merge.failed` avec `pr_already_merged` : l'entrée devient `merged`/`manual_merge` et l'aval se teste de nouveau sur la vraie cible (`AGENTS.md` D132) |
| Un membre de lot échoue à merger                                    | Résultat du job de merge                                                                                                                                                                                                                                                     | Les membres derrière lui dans le lot et tous les groupes en aval redémarrent ; seul le membre fautif passe en `failed`                                                                                                                                 |
| Rate limit primaire (429, ou 403 avec `x-ratelimit-remaining: 0`)   | En-têtes                                                                                                                                                                                                                                                                     | Le suivi de budget par connexion met en pause tous ses jobs jusqu'au reset ; une exécution attend au lieu d'échouer pendant 15 min, puis `merge_rate_limit_exceeded` sur le chemin de merge ou `start_test_run_retry_exhausted` à l'assemblage |
| Rate limit secondaire (403 avec `Retry-After`)                      | En-têtes                                                                                                                                                                                                                                                                     | Même suivi, backoff exponentiel, alerte au-delà de 3 occurrences par heure                                                                                                                                                                             |
| 422 à l'assemblage (validation, par ex. ref existante)              | Code HTTP                                                                                                                                                                                                                                                                    | L'exécuteur relit la ref et continue si elle correspond déjà ; sinon 5 tentatives puis `start_test_run_retry_exhausted`. Une autre erreur passagère (5xx, 429, arrêt) ne compte pas : le job attend jusqu'à 15 minutes après le début de l'exécution (`AGENTS.md` D133) |
| Conflit de merge à l'assemblage                                     | 409 sur l'API merges                                                                                                                                                                                                                                                         | Sur le merge du membre : `start_test_run_merge_conflict`, avec en `conflict_culprit` la branche cible ou la PR devant lui que l'exécuteur identifie en rejouant les merges (`docs/ALGORITHMS.md`) ; l'entrée échoue, ses dépendants redémarrent. Sur le merge d'un prédécesseur : le job réessaie, l'exécution de ce prédécesseur décide                                                                                                                  |
| La protection de branche bloque la branche de test                  | 403 à la création de ref                                                                                                                                                                                                                                                     | `start_test_run_permissions_block_test_branch` ; remonté par le vérificateur de configuration                                                                                                                                                          |
| Push extérieur sur la cible                                         | `push` dont le `sender` n'est pas le bot et dont le `after` n'est pas un `merged_sha` enregistré                                                                                                                                                                             | Toutes les exécutions sont invalidées, les groupes redémarrent avec `manual_push_to_target_branch`                                                                                                                                                     |

| Bascule Postgres                                                    | Erreurs de connexion                                                                                                                                                                                                                                                         | le pool sqlx rouvre ses connexions ; une réconciliation en vol échoue et est rejouée ; jobs et outbox survivent                                                                                                                                                  |

| Installation suspendue ou App désinstallée                          | Webhook `installation`                                                                                                                                                                                                                                                       | Fait `access.lost` : les files passent en `paused` avec la raison `access_lost` ; les entrées restent ; la reprise les revalide                                                                                                                                  |

Au démarrage, chaque réplique du scheduler marque les files qui ont une entrée vivante (`AGENTS.md` D131). Boucle de réparation (`AGENTS.md` D127). Le plan demande les lectures dues, et chacune rend ses faits par `queue_inbox` : chaque PR vivante est relue toutes les 15 minutes (`refresh_prs`) ; les checks du SHA de test d'une exécution `in_progress` sans rapport depuis 10 minutes sont relus toutes les 10 minutes (`refresh_checks`), qui recrée aussi au SHA de test une branche de test supprimée ; la tête de la cible est relue toutes les 5 minutes tant que la file a du travail, ou chaque minute tant qu'elle ne la connaît pas (`refresh_target`, fait `target.pushed` sans `before` ni `sender_id`). Le push d'un merge de la file peut arriver avant le fait du merge : tant qu'un job `merge_pr` de la file attend ou tourne, une livraison de push sur la cible dont le SHA n'est pas un merge connu attend la réconciliation suivante, et `refresh_target` ne lit pas la tête. Quand une branche a plusieurs files, le routage ne donne un push à aucune d'elles (`AGENTS.md` D135) : la passe des livraisons de la connexion demande `refresh_target` à chacune. À chaque nouvelle tête de la cible, `load_config` lit le fichier de configuration (`AGENTS.md` D136) ; il n'écrit rien si la cible a bougé depuis, et un fichier refusé laisse la file sur le dernier fichier valide. La fonction `resync` de `cihub-mergequeue` demande toutes ces lectures en classe `interactive` (D128) ; sa route arrive au lot 9.

Modes dégradés, par connexion, décidés par le budget du SCM et la boucle de réparation, affichés dans l'interface avec leur cause :

| Mode                 | Entrée                                                 | Ce qui continue                                                        | Ce qui s'arrête                                                         | Sortie                                                           |
| -------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `normal`             | —                                                      | Tout                                                                   | —                                                                       | —                                                                |
| `throttled`          | Budget restant sous 20 %, ou limite secondaire touchée | Commandes, statuts, merges des groupes déjà verts                      | Nouvelles branches de spéculation ; la fenêtre se contracte au plancher | Budget au-dessus de 40 % pendant 5 min                           |
| `scm_unavailable`    | 3 échecs réseau ou 5xx consécutifs sur la connexion    | Ingestion, journal, décisions ; les jobs s'accumulent avec leur classe | Tout appel sortant sauf une sonde toutes les 30 s                       | Sonde réussie ; rejeu des jobs par classe, `interactive` d'abord |
| `paused`             | Admin, ou connexion suspendue par le SCM               | Ingestion et journal ; les PR peuvent être soumises                    | Décisions et effets                                                     | Reprise par un admin, avec revalidation des entrées              |

Ces modes valent pour une connexion ; une panne de Postgres arrête tout processus, par construction, et la reprise se fait par rejeu de l'inbox et des baux expirés. La résilience se prouve par des tests d'injection de panne exécutés en intégration continue : un simulateur GitHub qui rend au hasard des 5xx, des 429, des webhooks perdus, dupliqués ou désordonnés, et des scheduler tués à des instants aléatoires, avec pour oracle qu'à la fin chaque PR verte est mergée exactement une fois, dans l'ordre du graphe, et que chaque PR rouge porte une raison. Un exercice de chaos mensuel rejoue la même chose sur l'instance de staging.

Règles de cohérence que le réconciliateur impose à chaque passage, et qu'un job nocturne vérifie aussi sur toute la base : chaque entrée `testing` appartient à exactement un groupe ayant une exécution en cours ; une entrée d'un groupe vivant a l'état de son groupe, sauf dans un groupe `tests_passed`, dont les premiers membres peuvent déjà être `merged` ; chaque `predecessor_ids` d'un groupe vivant a mergé, ou est vivant et devant lui dans l'ordre ; le nombre d'exécutions en cours hors bissection ne dépasse jamais le plafond de la fenêtre ; une entrée en `tests_passed` a une exécution réussie, et aucun push hors de la file n'est arrivé après la formation de son groupe ; `is_current` est vrai pour au plus une entrée par PR.

GitHub est la source de vérité de l'état git, Postgres celle de l'état de la file. En cas de désaccord (une PR que Postgres croit en file est en réalité mergée ou fermée sur GitHub), le réconciliateur croit GitHub et enregistre la transition avec `manual_merge` ou `pr_closed`. Une resynchronisation complète d'une file (`POST /queues/{id}:resync`, admins seulement) relit depuis GitHub chaque PR vivante et chaque exécution en cours : c'est la sortie de secours après un incident.

Des limites de capacité protègent la base partagée : au plus 500 entrées vivantes par file, 20 Mo par envoi de cibles impactées, 2 000 livraisons de webhooks par minute et par connexion avant que les livraisons ne passent en priorité basse, et 100 jobs en vol par connexion.
