# Reliability and failure handling

The correctness promise of the queue is that a PR is merged only after a successful test run on a commit whose tree equals what the target branch will contain; the resilience promise is that no intention is ever lost: a submission, a command, a check result survive crashes, lost webhooks, GitHub outages and concurrent operators, and are at worst delayed. The mechanisms are the event log, idempotent convergence toward a desired state, the repair loop, the scheduled SCM budget, and explicit degraded modes rather than implicit behaviors under stress.

| Failure                                                             | Detection                                                                                                                                                                                                                                                                    | Treatment                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Scheduler crash during a reconciliation                             | The transaction is rolled back; the transaction lock is released                                                                                                                                                                                                             | The next replica replays the reconciliation from the same state; no partial write exists                                                                                                                                                              |
| Worker crash during a job                                           | `locked_until` expires                                                                                                                                                                                                                                                       | The job is resumed; each executor reads GitHub first (does the branch exist? is the PR merged? does the comment exist?) and skips the steps already done through the `idempotency_key` of each step                                                   |
| Lost GitHub webhook (GitHub does not retry a failed delivery)       | The inbox insert precedes any processing and answers in under 2 s; a sweep every 5 minutes (`sweep_deliveries` job, `DECISIONS.md` D88) lists the attempts of the last 10 minutes through `GET /app/hook/deliveries` and redelivers the ones absent from the inbox; the tick rereads the live PRs and the silent runs | A delay of at most one sweep or one tick, never a lost transition                                                                                                                                                                                      |
| Out-of-order webhooks                                               | `received_at` and GitHub timestamps                                                                                                                                                                                                                                          | Sequential processing per queue; a `check_run` for a SHA that no run expects is stored then ignored                                                                                                                                                   |
| Duplicate webhook delivery                                          | `X-GitHub-Delivery` unique in `webhook_inbox`                                                                                                                                                                                                                                | The second insert has no effect                                                                                                                                                                                                                        |
| GitHub 5xx at merge                                                 | HTTP code                                                                                                                                                                                                                                                                    | The `merge_pr` job retries the call with the backoff, then gives `merge_repeated_server_errors` after 6 attempts, about 60 s (`DECISIONS.md` D123)                                                                                                     |
| GitHub 405 "merge already in progress"                              | HTTP code                                                                                                                                                                                                                                                                    | Retry with backoff; before giving up, read the PR: merged = success, open and on the base = close without resubmitting, otherwise `merge_already_in_progress`                                                                                          |
| GitHub 403 at merge for a stacked PR (D171)                         | HTTP code and message that names the asynchronous endpoint | Merge again through `merge-async` as a direct merge; `pending` or `409` = retry with backoff, `merged` = success, `failed` or `400` = `merge_rejected`; at the end of the attempts, `merge_already_in_progress` |
| 409 at merge (different `sha`)                                      | HTTP code                                                                                                                                                                                                                                                                    | `pr_updated_at_merge_time`; the item fails, the user resubmits                                                                                                                                                                                         |
| PR merged outside the queue                                         | The `merge_pr` job reads the PR before merging it                                                                                                                                                                                                                            | `merge.failed` with `pr_already_merged`: the item becomes `merged`/`manual_merge` and the downstream tests again on the real target (`DECISIONS.md` D132) |
| A batch member fails to merge                                       | Result of the merge job                                                                                                                                                                                                                                                      | The members behind it in the batch and all downstream groups restart; only the faulty member goes to `failed`                                                                                                                                          |
| Primary rate limit (429, or 403 with `x-ratelimit-remaining: 0`)    | Headers                                                                                                                                                                                                                                                                      | The per-connection budget tracking pauses all its jobs until the reset; a run waits instead of failing for 15 min, then `merge_rate_limit_exceeded` on the merge path or `start_test_run_retry_exhausted` at assembly                                  |
| Secondary rate limit (403 with `Retry-After`)                       | Headers                                                                                                                                                                                                                                                                      | Same tracking, exponential backoff, alert beyond 3 occurrences per hour                                                                                                                                                                                |
| 422 at assembly (validation, for example an existing ref)           | HTTP code                                                                                                                                                                                                                                                                    | The executor rereads the ref and continues if it already matches; otherwise 5 attempts then `start_test_run_retry_exhausted`. Another transient error (5xx, 429, shutdown) does not count: the job waits up to 15 minutes after the start of the run (`DECISIONS.md` D133) |
| Merge conflict at assembly                                          | 409 on the merges API                                                                                                                                                                                                                                                        | On the merge of the member: `start_test_run_merge_conflict`, with as `conflict_culprit` the target branch or the PR ahead of it that the executor identifies by replaying the merges (`docs/ALGORITHMS.md`); the item fails, its dependents restart. On the merge of a predecessor: the job retries, the run of that predecessor decides |
| Branch protection blocks the test branch                            | 403 at ref creation                                                                                                                                                                                                                                                          | `start_test_run_permissions_block_test_branch`; reported by the configuration checker                                                                                                                                                                  |
| External push on the target                                         | `push` whose `sender` is not the bot and whose `after` is not a recorded `merged_sha`                                                                                                                                                                                        | All runs are invalidated, the groups restart with `manual_push_to_target_branch`                                                                                                                                                                       |
| Test branch superseded while its CI is still running                | Run marked `interrupted`                                                                                                                                                                                                                                                     | Draft PR closed and branches deleted after `keep_test_branches_minutes` (`DECISIONS.md` D117); workflows cancelled if `actions: write` is granted (after Lot 6, D116); late reports stored then ignored (D118)                                         |
| Postgres failover                                                   | Connection errors                                                                                                                                                                                                                                                            | the sqlx pool reopens its connections; a reconciliation in flight fails and is replayed; jobs and outbox survive                                                                                                                                       |
| ClickHouse unavailable                                              | Insert errors                                                                                                                                                                                                                                                                | Outbox rows accumulate with backoff; merges are not affected; alert at 10 min of lag                                                                                                                                                                   |
| Customer webhook endpoint unreachable                               | Non-2xx response                                                                                                                                                                                                                                                             | Retries over 24 h, endpoint disabled after 7 days, visible in the dashboard                                                                                                                                                                            |
| Installation suspended or App uninstalled                           | `installation` webhook                                                                                                                                                                                                                                                       | Fact `access.lost`: the queues go to `paused` with the reason `access_lost`; the items remain; the resume revalidates them                                                                                                                             |

At startup, each scheduler replica marks the queues that have a live item (`DECISIONS.md` D131). Repair loop (`DECISIONS.md` D127). The plan requests the due reads, and each one returns its facts through `queue_inbox`: each live PR is reread every 15 minutes (`refresh_prs`); the checks of the test SHA of an `in_progress` run without a report for 10 minutes are reread every 10 minutes (`refresh_checks`), which also recreates a deleted test branch at the test SHA; the head of the target is reread every 5 minutes as long as the queue has work, or every minute as long as it does not know it (`refresh_target`, fact `target.pushed` without `before` or `sender_id`). The push of a queue merge can arrive before the fact of the merge: as long as a `merge_pr` job of the queue is waiting or running, a push delivery on the target whose SHA is not a known merge waits for the next reconciliation, and `refresh_target` does not read the head. When a branch has several queues, routing gives a push to none of them (`DECISIONS.md` D135): the connection deliveries pass requests `refresh_target` from each of them, after the end of a merge in flight of one of these queues, as for a single queue (D150). At each new head of the target, `load_config` reads the configuration file (`DECISIONS.md` D136); it writes nothing if the target has moved since, and a rejected file leaves the queue on the last valid file. The `resync` function of `cihub-mergequeue` requests all these reads in class `interactive` (D128); its route arrives in Lot 9.

Degraded modes, per connection, decided by the SCM budget and the repair loop, shown in the interface with their cause:

| Mode                 | Entry                                                  | What continues                                                         | What stops                                                              | Exit                                                             |
| -------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `normal`             | —                                                      | Everything                                                             | —                                                                       | —                                                                |
| `throttled`          | Remaining budget under 20%, or secondary limit hit     | Commands, statuses, merges of the groups already green                 | New speculation branches; the window contracts to the floor             | Budget above 40% for 5 min                                       |
| `scm_unavailable`    | 3 consecutive network or 5xx failures on the connection | Ingestion, log, decisions; jobs accumulate with their class           | Every outgoing call except a probe every 30 s                           | Successful probe; replay of the jobs by class, `interactive` first |
| `paused`             | Admin, or connection suspended by the SCM              | Ingestion and log; PRs can be submitted                                | Decisions and effects                                                   | Resume by an admin, with revalidation of the items               |

These modes apply to a connection; a Postgres outage stops every process, by construction, and recovery happens by replay of the inbox and of the expired leases. Resilience is proven by fault injection tests run in continuous integration: a GitHub simulator that randomly returns 5xx, 429, lost, duplicated or out-of-order webhooks, and schedulers killed at random instants, with as oracle that at the end every green PR is merged exactly once, in graph order, and that every red PR carries a reason. A monthly chaos exercise replays the same thing on the staging instance.

Consistency rules that the reconciler enforces at each pass, and that a nightly job also checks over the whole database: each `testing` item belongs to exactly one group that has a run in progress; an item of a live group has the state of its group, except in a `tests_passed` group, whose first members may already be `merged`; each `predecessor_ids` of a live group has merged, or is live and ahead of it in order; the number of runs in progress outside bisection never exceeds the window ceiling; an item in `tests_passed` has a successful run, and no push from outside the queue arrived after the formation of its group; `is_current` is true for at most one item per PR.

GitHub is the source of truth for the git state, Postgres for the queue state. In case of disagreement (a PR that Postgres believes in the queue is actually merged or closed on GitHub), the reconciler believes GitHub and records the transition with `manual_merge` or `pr_closed`. A full resynchronization of a queue (`POST /queues/{id}:resync`, admins only) rereads from GitHub each live PR and each run in progress: it is the emergency exit after an incident.

Capacity limits protect the shared database: at most 500 live items per queue, 20 MB per impacted targets upload, 2,000 webhook deliveries per minute and per connection before deliveries drop to low priority, and 100 jobs in flight per connection.
