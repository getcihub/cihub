# Competitive analysis

All serious merge queues converge on the same core (test the PR on top of those that precede it, remove the culprit, rebuild behind) and diverge on four points: where the CI runs, how failures are absorbed, how it scales, and how far the user can express their rules. Eight products and four experience reports were reviewed (official documentation, public tickets, engineering articles); the table summarizes what each one brings and where it breaks.

| Product                                                                                                                                                           | Queue model                                                                                    | Where the CI runs                                                                       | Failure                                                                                                    | Scaling                                                                                         | Distinctive idea                                                                                                                                 | Observed limit                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| [Trunk](https://docs.trunk.io/merge-queue/merge-queue)                                                                                                            | Speculative FIFO, parallel mode by impacted targets, batches + bisection                       | `trunk-merge/*` branches with optional draft PR                                         | Pending failure until the predecessors conclude, configurable depth, optimistic merge                      | Fixed concurrency (5 to 50)                                                                     | Cache of results during bisection, reconciliation independent of webhooks                                                                        | Little expressiveness: only status checks govern                                                                                            |
| [Mergify](https://docs.mergify.com/merge-queue/)                                                                                                                  | One train per branch; a named `queue_rule` is a set of settings that a PR takes by its `queue_conditions`; serial / parallel (scopes) / isolated modes | Cumulative draft PRs `mergify/merge-queue/*`, or in place on the PR in serial mode  | Batches split then bisected, `max_checks_retries`, automatic timeout at p95, `skip_intermediate_results`   | `max_parallel_checks` up to 128, dynamic batch size                                             | Conditions language (\~80 attributes), separation of entry conditions / merge conditions, scheduled freezes, 45 removal reasons                  | Check detection delays of 9 to 46 min in Sept. 2026 (tickets #5177, #5183), unstable configuration surface                                  |
| [GitHub native](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) | Speculative FIFO per branch, merge groups                                                      | `gh-readonly-queue/*` branches and `merge_group` event                                  | Culprit removed, rebuild behind; "jump to top" rebuilds everything                                         | 1 to 100 groups in parallel                                                                     | Zero installation, integrated with rulesets                                                                                                      | A single set of checks for PR and group (path-filtered workflows block the queue), `merge_group` sometimes never emitted, no batches        |
| [GitLab merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/)                                                                                         | Train per target branch                                                                        | Merged results pipelines                                                                | The faulty car leaves, the following ones are recomposed                                                   | 20 pipelines in parallel by default                                                             | Native integration with GitLab CI                                                                                                                | No batches nor bisection, a direct push restarts everything                                                                                 |
| [bors / rust-lang bors](https://bors.tech/documentation/)                                                                                                         | A single batch under test, strict serial                                                       | Push to `staging`, then fast-forward of `master`                                        | Binary bisection of the batch                                                                              | No parallelism                                                                                  | The tested commit is the commit that lands; `try`, `rollup`, `treeclosed`                                                                        | Throughput bounded by CI duration; bors-ng and homu archived                                                                                |
| [Zuul](https://zuul-ci.org/docs/zuul/latest/gating.html)                                                                                                          | Multi-repository dependent pipelines, future state of the dependencies served to the jobs      | Zuul is the CI                                                                          | The culprit leaves, the following ones are rebased on the nearest healthy element                          | Adaptive window (20 by default, floor 3, linear growth, exponential decrease)                   | TCP-like window, cross-repository `Depends-On`, twenty years of production at OpenStack                                                          | Requires adopting Zuul as the CI                                                                                                            |
| [Aviator](https://docs.aviator.co/mergequeue/concepts/parallel-mode)                                                                                              | Serial, parallel by affected targets, batches                                                  | Draft PRs on temporary branches, optional fast-forward                                  | Queue reset in parallel mode, optimistic validation, parallel bisection                                    | `max_parallel_builds`, up to 1 M targets per account                                            | Classification of failures by reading the logs ("is the cited file modified by the batch?"), targeted resume of a job                           | Resets expensive in CI, heavy configuration                                                                                                 |
| [Graphite](https://graphite.com/docs/graphite-merge-queue)                                                                                                        | Whole stacks in queue, parallel CI on A, A←B, A←B←C                                            | `gtmq_*` draft PRs                                                                      | Culprit removed, dependent runs cancelled, batches bisected                                                | Configured concurrency (4 internally)                                                           | Designed for stacked PRs                                                                                                                         | GitHub only, incompatible with the native queue                                                                                             |
| [Shopify](https://shopify.engineering/successfully-merging-work-1000-developers)                                                                                  | Predictive branch simulating the future `master`, batches of 8, 3 CI batches ahead             | Predictive branch                                                                       | Tolerance threshold: 3 consecutive failures before removal, 0.39 % false removals at 25 % flakiness        | 400 commits per day, 1,000 developers                                                           | Reconciliation loop desired state / GitHub state, incident lock that lets the CI run                                                             | Internal                                                                                                                                    |
| [Uber SubmitQueue](https://arxiv.org/html/2501.03440v2)                                                                                                           | Speculation tree, probabilistic selection of builds under budget                               | Internal build                                                                          | Conflict analyzer on the build graph to prove independence                                                 | Thousands of changes per day                                                                    | Logistic regression (97 % precision) to choose what to speculate, build duration prediction, bypass of large blocking changes                    | Internal, requires a build graph                                                                                                            |

What CIHub keeps, and from where:

| Idea                                                      | Origin                                        | What we do with it                                                                                                                                                                                                            |
| --------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adaptive speculation window                               | Zuul                                          | Test concurrency is not a fixed number: it grows after each success and shrinks after each failure, between a floor and a ceiling; it is the cheapest defense against flaky test storms                                       |
| Rebuild on the nearest healthy element                    | Zuul, GitLab, GitHub                          | A failure removes only the culprit; never a reset of the whole queue                                                                                                                                                          |
| Tolerant failure budget                                   | Shopify, Chromium, Aviator                    | A single failure never removes a PR; we count consecutive failures, restart in a targeted way, and cross-check with tests known as flaky                                                                                      |
| Batches and bisection                                     | bors, Mergify, Aviator, Graphite              | For long CIs, O(log N) runs per failure instead of N, with cache of intermediate results                                                                                                                                      |
| Independent queues per impacted targets                   | Uber, Aviator, Trunk, Mergify                 | The number one throughput lever on a monorepo; computed by overlap, never by hand-named lanes                                                                                                                                 |
| Entry conditions distinct from merge conditions           | Mergify, most frequent request on GitHub      | A small conditions language, not an 80-attribute DSL                                                                                                                                                                          |
| Desired state and reconciliation loop                     | Shopify                                       | The queue is an event log; the reconciler computes the desired git state and makes it converge, idempotently, which makes lost webhooks, GitHub outages and restarts recoverable                                              |
| The tested commit is the commit that lands                | bors, Aviator, Graphite                       | `fast_forward` merge method in addition to squash, merge and rebase, when branch protection allows it                                                                                                                         |
| Enumerated removal reasons and explicit batch statuses    | Mergify                                       | Already in the domain model; each queue exit has a named cause and a page                                                                                                                                                     |

What CIHub does differently. None of these products is at the same time open source, self-hostable in one command and multi-tenant: bors was but does not speculate, Zuul is but imposes its CI, the others are SaaS. None treats the GitHub budget as a resource to schedule, while the Mergify delays of September 2026 come from there: in CIHub, each GitHub call carries a priority class (human commands, merges, speculation, catch-up) and speculation is the first thing sacrificed when the budget drops. None keeps the test history at the case level with the queue as the experimental source of truth: CIHub exploits bisections as controlled experiments to qualify flaky tests. Finally, the common failures noted everywhere (required check that never reports, `merge_group` never emitted, removal without a readable reason, full rebuild after a priority) each have a named answer in [RELIABILITY.md](RELIABILITY.md) and [ALGORITHMS.md](ALGORITHMS.md).

The command line. Trunk groups its queue commands under one product (`trunk merge <pr>`, `trunk merge status|cancel|pause|resume`) and takes the repository from the working directory; Mergify groups them by feature (`mergify queue pause|unpause|status|show`) with a global `-r, --repository <owner/repo>` that falls back to `GITHUB_REPOSITORY`. CIHub takes the structure, not the interface: one command line with one group per module (`cihub queue …`), apart from the binary of the server (`cihub-server …`), a `--repo <owner/name>` option that falls back to the `origin` remote of git, no implicit verb (`trunk merge 12`), no shortcut at the top level, and no variable named after an SCM.
