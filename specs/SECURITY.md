# Security and multi-tenancy

Tenancy is enforced on three layers: row level security in Postgres (and row policies in ClickHouse when it is enabled), organization-scoped identifiers at the API, and one GitHub installation token per installation, never shared between organizations. Nothing of one tenant can be inferred from the data of another, including through response time, because the reconcilers are per queue and the workers filter every query by `queue_id`.

- Users sign in through the user authorization of the GitHub App, with PKCE (`specs/GITHUB.md`); a CIHub organization is attached to one or more SCM accounts, for example a GitHub organization, and the roles come from the GitHub membership of the connection (owners become `admin`, members `member`), refreshed every hour. A `member` reads the queues and submits, cancels and restarts PRs; an `admin` also changes the state and the configuration of a queue and reads the audit log. A `viewer` role for read-only dashboards and the change of a role by an admin come after lot 10d (`specs/LOTS.md`).
- API tokens have the form `cht_` followed by 20 random bytes in base32, are shown only once, stored as SHA-256 fingerprints, scoped to an organization with the scopes listed in [API.md](API.md), with optional expiration and last-use tracking, to the minute.
- A dashboard session is the cookie `__Host-cihub_session`, which holds `chs_` followed by 20 random bytes in base32 (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`: the prefix `__Host-` stops another subdomain from planting one, and a request that carries it twice is refused); Postgres keeps only its SHA-256 fingerprint. A session lasts 14 days; the sign-out deletes it and clears its cookies, and the daily maintenance deletes the expired ones. It is never accepted as an API token. A sign-in in progress keeps its `state`, its PKCE verifier and the page to open after in the cookie `__Host-cihub_sign_in` (`HttpOnly`, 10 minutes), cleared by the callback; that page is a path of the instance, never another site, which the server and the dashboard both check. The pages of the dashboard carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`: no other site frames a page whose buttons act. The role of its user in the organization of the URL gives its scopes; an organization where the user has no role answers `404`. Every request of a session but `GET`, `HEAD` and `OPTIONS` carries the header `X-CSRF-Token`: the hexadecimal SHA-256 of a label and the secret of the session, which the server keeps nowhere and gives to the scripts of the dashboard in the cookie `__Host-cihub_csrf` (readable by a script, same attributes otherwise). A submission from a session carries the account of its user: the job checks its permission on the repository, `write`, or `admin` for a direct merge, as for a command in a comment.
- A session of the command line holds `chc_` followed by 20 random bytes in base32, sent only in `Authorization: Bearer`; a session of the dashboard is accepted only in its cookie, and a session of the command line never in a cookie, so that one never stands for the other, and only a session of the dashboard approves a device code. Both live in `sessions`, as SHA-256 fingerprints. A session of the command line ends 90 days after its last use (each use pushes `expires_at` back, at most once an hour, so that a read does not write each time), or when `cihub auth logout` deletes it. A device code is two secrets: `device_code`, `chd_` followed by 20 random bytes, which only the command line knows and which Postgres keeps as a fingerprint, and `user_code`, 8 letters out of 20 (about 34 bits), which the person reads and types. Both expire after 15 minutes and serve once. The address that the command line shows never carries the code: the page `/device` asks the person to type it, then waits for a click on *Approve* or *Deny*, with the CSRF token of the session. A phishing of the code needs the person to type a code that someone else gave them, not one click on a link, and the page warns about a code that the person did not ask for. Guessing a user code needs a session of the dashboard, under its rate limit, and approving the code of someone else only gives them the session of the guesser. `POST /device-codes` and `POST /device-codes/token` need no token: the daily maintenance deletes the codes that expired, and a command line that asks sooner than `interval` gets `429 polling_too_fast`.
- The stream of an organization (`GET /orgs/{org}/stream`) checks its grant when it opens, as any route, then ends after 5 minutes: the browser opens it again with its session or token, so a revoked token, an ended session or a removed member hears the changes 5 minutes at most. A token or a person keeps 8 streams open at once; the ninth answers `429`.
- PRs from forks cannot carry secrets: `impacted-targets` therefore also accepts a GitHub Actions run identifier; CIHub verifies through the API that the run is in progress, belongs to the repository and matches the announced head SHA.
- The GitHub App private key, the webhook secret and the client secret of the App come from the environment or from the configuration file of `cihub-server`, which the operator feeds from its secret manager (Vault or the cloud KMS), and are read at startup into a `SecretString`. A configuration file that carries `database.url`, `github.private_key`, `github.webhook_secret` or `github.client_secret` is a secret: the operator protects it as such (a Kubernetes Secret rather than a ConfigMap, mode 0600), or leaves these keys to the variables; installation tokens are cached in memory only, and the token of a person who signs in is forgotten at the end of the sign-in. Customer webhook secrets are encrypted at rest with a per-organization data key.
- The `cihub-sudo` App is opt-in per organization, installed separately, and its token is used only by the `merge_pr` job for `force_enqueued` items; each of these merges is logged with the requesting user.
- Commands from PR comments are honored only for users who have `write` (or `admin` for `--direct`) on the repository; comments from the queue bot are ignored to avoid loops.
- The CIHub Postgres role is neither superuser nor `BYPASSRLS`, because it would see every organization: otherwise `cihub-server` refuses to start.
- Audit log: every setting change, pause, resume, drain, deletion, token creation and forced merge, with actor, IP and before/after values, kept 2 years.
- The internal address (`CIHUB_INTERNAL_ADDR`) is separate from the public routes and must not be exposed on the Internet. The `/healthz` and `/readyz` probes are open and give only the name and the version of the binary; `/metrics` is anonymous by default; with `CIHUB_PROMETHEUS_ANONYMOUS_ACCESS=false`, it requires an admin or machine user (session of the request). Its labels name installations and queues of several organizations: an installation whose internal address is reachable by third parties must disable anonymous access.
- All traffic is TLS 1.2 or higher; webhooks are verified with HMAC-SHA256 before any parsing; request bodies are capped at 25 MB; the dashboard uses same-site cookies and CSRF tokens.
- Data residency: each instance is self-contained and keeps its data where it runs; a host that serves several regions deploys several instances, with no replication between them.
